1. WHAT IS THIS PROJECT? (IN 3 SIMPLE SENTENCES)
--------------------------------------------------------------------------------
This project is an engineering queueing simulation web application for a Petrol Pump.
It calculates customer wait times, queue lengths, and pump utilization across 3 classical
single-server stochastic queueing models (M/M/1, M/G/1, and G/G/1).
The backend is built with modern C# ASP.NET Core (.NET 8) serving a responsive,
custom-themed web frontend directly from wwwroot.

3. MODERN SOFTWARE ARCHITECTURE (.NET 8 C# BACKEND)
--------------------------------------------------------------------------------
The project uses a clean, decoupled architecture:

1. STATIC FRONTEND (Hosted in wwwroot/):
   - index.html      : Clean single-server interface with real-time formula reference guide.
   - style.css       : Midnight navy and neon amber theme matching theme.jpg.
   - app.js          : Form controls, JSON payload submission, gauge & steps renderer.
   - queueModels.js  : Client-side mathematical engine providing offline resilience.
   - theme.jpg       : Background artwork for the petrol station theme.

2. ASP.NET CORE PIPELINE (Program.cs):
   - Configures Dependency Injection (DI) for QueueSimulationService.
   - Enables Cross-Origin Resource Sharing (CORS).
   - Serves static files and default index.html via UseDefaultFiles() & UseStaticFiles().
   - Maps REST API endpoints via MapControllers().

3. REST API CONTROLLER (Controllers/QueueController.cs):
   - [HttpPost("api/calculate")] : Receives user inputs and returns computed metrics.
   - [HttpGet("api/petrol-data")] : Serves baseline historical empirical distribution stats.

4. SIMULATION SERVICE & MATH ENGINE (Services/QueueSimulationService.cs):
   - Strongly-typed service implementing IQueueSimulationService.
   - Normalizes all input units (seconds, minutes, hours) into the user's display unit.
   - Enforces system stability validation (rho < 1.0).
   - Generates exact formula substitution steps for transparency.

5. DATA TRANSFER OBJECTS (Models/):
   - QueueInputModels.cs  : Models request contract (Model, DisplayUnit, Arrival, Service).
   - QueueResultModels.cs : Models response contract (Results array, Steps array, Error).
   - PetrolDataPreset.cs  : Holds the 300-vehicle baseline dataset parameters.

4. DATA INPUT & OPERATIONAL DYNAMICS
--------------------------------------------------------------------------------
The user/teacher can enter values in seconds, minutes, or hours, as either:
- "Mean Time" (e.g. 45 seconds between car arrivals)
- "Rate" (e.g. 1.33 cars arriving per minute)

INPUT FIELDS:
- Arrival Side: Mean inter-arrival time / rate (plus standard deviation for G/G/1).
- Service Side: Mean fueling service time / rate (plus standard deviation for M/G/1 and G/G/1).

DEMO TEST CASES TO SHOW YOUR TEACHER:

Normal Smooth Flow:
- Arrival Mean Time = 45 seconds (lambda = 1.33 cars/minute)
- Service Mean Time = 30 seconds (mu = 2.00 cars/minute)
- Result:
  * Utilization: rho = 30 / 45 = 0.6667 (66.67% busy)
  * System is stable (rho < 1.0), short queue, smooth operation.

Bottleneck / Near-Saturation Flow:
- Arrival Mean Time = 40 seconds
- Service Mean Time = 38 seconds
- Result:
  * Utilization: rho = 38 / 40 = 0.95 (95% busy, gauge turns red)
  * Queue length (Lq) and wait time (Wq) increase sharply.

Unstable / Infinite Queue Test:
- Arrival Mean Time = 30 seconds (car arrives every 30s)
- Service Mean Time = 45 seconds (pump takes 45s to fuel)
- Result:
  * rho = 45 / 30 = 1.50 (rho >= 1.0)
  * System rejects calculation with error:
    "The system is unstable: utilization rho = 1.5 must be below 1."

5. KEY SYMBOLS YOU MUST KNOW (TEACHER VIVA CHEAT-SHEET)
--------------------------------------------------------------------------------
Symbol   What it Means                  In Plain English
--------------------------------------------------------------------------------
lambda   Arrival Rate                   Cars arriving per unit time (1 / Mean Arrival)
mu       Service Rate                   Cars fueled per unit time (1 / Mean Service)
rho      Pump Utilization               Fraction of time pump is busy: rho = lambda / mu
Lq       Queue Length                   Average number of cars WAITING in line
L        System Length                  Average total cars at station (in line + at pump)
Wq       Waiting Time in Queue          Average time a driver waits before fueling starts
W        Total Time in System           Wait time + Fuel time: W = Wq + (1 / mu)
P0       Empty Probability              Chance the station has zero cars: P0 = 1 - rho

CRITICAL STABILITY CONDITION:
"rho must be strictly LESS than 1 (rho < 1.0). If rho >= 1.0, arrivals exceed
pump capacity, causing an infinite queue buildup."

LITTLE'S LAW:
- L  = lambda * W    (Total cars = Arrival rate * Total time in system)
- Lq = lambda * Wq   (Cars in queue = Arrival rate * Waiting time in queue)
- W  = Wq + (1 / mu) (Total time = Waiting time + Service time)

6. THE 3 SINGLE-SERVER QUEUE MODELS
--------------------------------------------------------------------------------

MODEL 1: M/M/1 (Single Server, Exponential Arrival & Service)
- Description: 1 pump. Arrivals follow a Poisson process; fueling time is Exponential.
- Formulas:
    Lq = rho^2 / (1 - rho)
    P0 = 1 - rho
- Use case: Classic baseline with purely random arrivals and service.

MODEL 2: M/G/1 (Single Server, General Service Distribution with Variance)
- Description: 1 pump. Arrivals are Poisson, but fueling time has custom standard deviation (sigma).
- Formula (Pollaczek-Khinchine Formula):
    Lq = [ lambda^2 * sigma_s^2 + rho^2 ] / [ 2 * (1 - rho) ]
- Takeaway: Mathematically proves that variability in service time directly increases
  customer waiting time even if the average service speed remains unchanged.

MODEL 3: G/G/1 (Single Server, General Arrival & General Service)
- Description: 1 pump. Both arrival and service distributions have custom standard deviations.
- Formula (Sakasegawa Single-Server Approximation):
    Ca^2 = (sigma_a / Mean_a)^2
    Cs^2 = (sigma_s / Mean_s)^2
    Wq ≈ [ rho / (1 - rho) ] * [ (Ca^2 + Cs^2) / 2 ] * (1 / mu)
    Lq = lambda * Wq
- Takeaway: Models realistic station operations without restricting to exponential curves.

7. TOP 5 VIVA QUESTIONS & DIRECT ANSWERS
--------------------------------------------------------------------------------

Q1: Why did you build the backend using ASP.NET Core (.NET 8)?
Answer:
"ASP.NET Core (.NET 8) provides high performance, type safety, and clean separation
of concerns. The C# QueueSimulationService strongly types stochastic calculations,
while UseDefaultFiles() and UseStaticFiles() allow hosting the web dashboard from wwwroot."

Q2: What is Kendall's Notation in M/M/1, M/G/1, and G/G/1?
Answer:
"The 1st letter represents arrival distribution ('M' = Markovian/Poisson, 'G' = General).
The 2nd letter represents service distribution ('M' = Exponential, 'G' = General).
The number '1' denotes a single server (one petrol pump)."

Q3: What is 'rho' (Utilization) and why must it be below 1?
Answer:
"rho = lambda / mu represents the fraction of time the pump is busy.
It must be strictly less than 1 (rho < 1) for the queue to reach steady-state.
If rho >= 1, vehicles arrive faster than they can be fueled, causing infinite queue growth."

Q4: What is Little's Law?
Answer:
"Little's Law proves that L = lambda * W and Lq = lambda * Wq. It directly connects
the average number of cars in the system to the arrival rate and average waiting time."

Q5: What is the significance of the Pollaczek-Khinchine formula in M/G/1?
Answer:
"It calculates queue length when service time has variance:
Lq = (lambda^2 * sigma^2 + rho^2) / [2 * (1 - rho)].
It proves that higher variation in fueling times (sigma^2) increases line delays,
highlighting the need for standardized fueling procedures."
